## Order

1. Start S01, S02, S03, S04, S05, S06 and S10 in parallel against declared ports/fakes. Integrate S01-S06; run import and read-back on real SQL before waiting on publish. S09 starts once those bodies land. None waits on the frame-format commit or P09.
2. S07 and S08 can also be built in parallel using SQL watermark fixtures and fake ports. S07 **cannot authorize real retirement until PS-2 P09 commits the publish watermark after registry CAS**. S08 can report import/read-back results before that, with files held. S11 import/read-back wiring starts after the leaf bodies; coordinate edits with the PS-2 server wiring owner.
3. After P09, finish S11's real publish/retire and replication proof, then run all named suites and the memory mutant. P09 may itself wait on the frame-format commit; PS-3 has no direct dependency on frames. Never substitute “rows exist” or “head uploaded” for a committed watermark.

## Hosts: interfaces only

Desktop D6 supplies the #2116 streaming reader for `pdpp-collection-state.json`, one retained PDPP record at a time. It passes verified artifact digest, stream, immutable upload revision and install identity through the authenticated existing seed route (S06/S11), with <=4 MiB batches including envelope overhead. It keeps D6 until every stream receipt is read back and published; erase is id/path/hash fenced. Its native reader retains #2116's <12 MiB above warm baseline bound; PS's separate bound is <=48 MiB. Stop legacy sinks before snapshotting. The host default for streamSync.retireLegacy stays false.

Phone P7 supplies replayable, immutable snapshots through the same source/upload contract, scoped to signed-in owner/network and verified declaration. The phone owns snapshot completeness, hash-fenced erase, and its local switch fence. P1/P2 are **not imported**: delete only after re-collection publishes (F.3 correction). Do not conflate that host job with P7 import. Web supplies no legacy import source. Both hosts consume receipt/proof ports through the published localdb export; no connector package learns legacy data-set names, and bindings.ts stays unchanged.

## Open questions and recommended answers

1. F.3 refers to r4 placement, while PLAN-1109's earlier phone list says to import P1/P2/P7. Recommendation: use r5's explicit correction: import only P7; P1/P2 wait for re-collection publish. Confirm the remaining host cleanup inventory with D1/P1 owners before any delete is enabled. These interfaces give no authority to delete unlisted stores.
2. Must a newer DB value excuse an older legacy value? Recommendation: no new exception in PS-3. Exact row and projection mismatch holds the copy with a reason; the owner can approve a later PDPP-aware coverage rule. Do not resurrect #595's connector-specific entity/count rules. Conservative holds can delay retirement but cannot lose data.
3. Multiple live canonical instances: #604 chose most recently active. Recommendation: hold ambiguous sources and report exclusions; do not silently discard other accounts' rows under a “nothing lost” claim. Resolving identity is a separate owner decision, not a new connector-id table.
4. How should highest seq persist without adding a schema column? Settled: migration 2 adds nullable revision, generation and highest_seq columns; NULL holds. Never infer publication from wall time or row count.
5. How are declaration-free legacy transition rows handled? Recommendation: follow r5.2 §5: no new manifest schema, transition mapping or connector-id literal. Import only rows covered by existing verified declarations. Report all other stores/exclusions and retain them pending re-collection or an explicit later deletion policy.
6. What authorizes flag enablement? Recommendation: a separate product-owner release decision after S11 and host proofs. This branch and all builders keep the default false. A dry run has no erase capability regardless of configuration.
7. Can a source record itself exceed 4 MiB? Recommendation: refuse with a redacted reason and retain the source. Do not split one PDPP record into incompatible rows, silently skip it, or exceed the route bound. Blob bytes remain at their existing owner; this design does not authorize garbage collection of referenced blobs.
8. What pins upload revision and canonical snapshots? Recommendation: host seals staged NDJSON with digest before import; Node quiesces the switched legacy writer and binds a source revision to its canonical snapshot. Detect mutation between passes and refuse. A mutable directory path alone is never a revision.
