## Order

S09 compares fresh-child RSS at 1x and 4x input; S11 verifies the server's own import and retire. Publication uses PS-2's existing database owner and does not gate removal of obsolete files.

## Full replacement (Tim, 11-10)

The database is authoritative. Old files are a one-time seed with stamp `(0, "seed")`; any real write wins. Read-back checks the seed that was read, permits newer database values, and reports failures as bugs. It never grants or withholds removal authority.

Only stores present in the host-supplied frozen bindings, with a verified declaration and primary key, are imported. Unsupported stores and missing proof are counted. Of several old accounts for one source, the most recently active live account wins, using the same recency rule as #604; the others are counted. All old files are included when removal is enabled. Import accepts the same record sizes as run intake. Page byte targets batch small rows and allow a single larger row alone. The memory scaling test uses the same row size at 1x and 4x input.

Removal stays off until Tim's dev-environment test. "Old files" means the Personal Server's own legacy store: the legacy `index.db` rows and the `data/` files that `openLegacyAccess` reads. Desktop's `pdpp_collection_state` seed rows are out of scope. The server imports and retires its own store; no host supplies a port. `createLegacyStoreRunner` (`packages/server/src/localdb/legacy-store-import.ts`) is the import waker's runner. For a switched owner it imports every importable source, then calls `retireLegacyCopies` with the server config's `streamSync`; retirement follows the import in the same run, because it also removes copies the import did not read. Import has no setting. `streamSync.retireLegacy` (default false) only decides whether files are removed; off, the same call reads back and reports. A server with a custom `dataDir` (not `<root>/data`) does not import. A seed already in the database wins over this store: both write stamp `(0, "seed")`, the merge keeps the existing row on an equal stamp, and a published stream's closed seed window refuses the import. It never fails the import or the start: a failure is logged and the next import run retries. A dry run cannot erase. Never reconnect a deleted connection. Erase compares exact id/path/hash under the existing storage lock, journals intent before unlink, and repairs the exact index row on crash recovery. Absence alone is reported; only matching intent proves an earlier erase. No manifest changes or connector-id tables are permitted.

## Leaf verification

S01-S10 have focused behaviour tests, as does the shared fingerprint helper. Lite also tests runtime admission, receipts, crash recovery and authoritative database values. S11 is the server-owned import and retire wiring, tested in `legacy-migration.test.ts` and `legacy-replication.test.ts`. Migration 3 adds a separate exact-copy erase-intent journal at the ledger owner. S05 records intent under the storage lock before unlink; S07 can reconcile exact absence with matching intent . Missing intent never proves an earlier erase. `CI=true npx tsc -b --noEmit` hits TS6310 for this repo's project references; use the repository's `CI=true npm run lint` (`tsc --build --force`) instead. Typecheck establishes interface compatibility only; it does not prove migration or deletion safety.
