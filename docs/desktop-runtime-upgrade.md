# Desktop runtime database upgrade

The Desktop runtime at `dde4ed94b710e074e93896b1c7d6dacc71883f23`
and main at `da4068d367febe8e69f7fb3af99d44db6d029127` use the same
physical `index.db`, with two independent migration counters:

| Runtime                      | Legacy index: `PRAGMA user_version` | Records: `pdpp_schema_version` |
| ---------------------------- | ----------------------------------- | ------------------------------ |
| Earlier Desktop (`4245639b`) | 15                                  | 14                             |
| Current Desktop (`dde4ed94`) | 15                                  | 15                             |
| Main before convergence      | 14                                  | 15                             |
| Converged                    | 17                                  | 16                             |

The counters identify different schemas. They must never substitute for each
other or decrease. Legacy index v15 adds `replacement_cursor` to Oura takeover
state. Main's records v15 adds the retained-history blob reference index;
Desktop's records v15 instead adds the Strava transition ledger. Records v16
adds both objects if absent, so either v15 lineage upgrades without losing
its existing state. These migrations are additive.
The converged runtime stamps the legacy index v17 as
a compatibility fence without further table changes. Both Desktop v15 and
main v14 indexes upgrade without dropping rows. The records counter advances
to v16. Each store rejects versions above its
supported version.
The shared database initializer and direct records-store opener use the same
two-counter preflight before switching journal mode or creating tables.
The initializer also checks before bootstrap can perform recovery work.
It checks the PDPP counter even when that store will not be mounted.

The conformance branch also used legacy v15 and v16 for other additive columns
(`pdpp_origin` and `generation`). It did not add `replacement_cursor`. The
converged runtime therefore adds that column whenever it is absent, including
on v15/v16 databases, and leaves existing rows without a replacement proof.
Legacy v17 keeps the convergence fence distinct from those earlier slots.
Branches that adopt this schema must retain its meaning or use v18 and above
for later migrations.

## Rollback

After the converged runtime opens the index, the old Desktop runtime refuses
`Unsupported index.db schema version 17; runtime supports 15`. This happens
before bootstrap can migrate local state, even when PDPP is disabled.
The current Desktop records store independently rejects PDPP v16 before the
startup blob sweep:
`pdpp_records database schema version 16 is newer than this build supports (15)`.
The earlier Desktop runtime supports only records v14 and also refuses v16.
Do not lower either counter to make an older runtime start. That would bypass
the compatibility check and could let its older garbage collector remove
retained-history blobs.

To roll back, stop the runtime and restore a consistent, complete pre-upgrade
Personal Server snapshot, including the database, data files, and durable
authorization state. A database copy alone does not restore matching data or
MCP authorization state. A restored snapshot also excludes writes made after
that snapshot. Keep the post-upgrade store separately if those writes are
needed. Otherwise use a runtime that supports both schemas and the current
authorization rules.

## Upgrade regression fixture

`packages/server/src/storage/__fixtures__/desktop-d-index.sql` contains the
synthetic schema and data generated with the earlier `4245639b` runtime, using its
`initializeDatabase`, `createSqliteRecordStore`, and `createLegacyScopeAuthority`.
The adjacent JSON records pagination and sync cursors issued by that runtime.
It includes generation-2 Oura bindings, replacement proofs, completion receipts
for all three Oura streams, deleted records, version history, a live blob, and
a blob referenced only by retained history. Its epoch is fixed for repeatable
cursor assertions. The test loads this fixture without Git or an older build.

`desktop-line-upgrade.test.ts` checks every application table's rows across
migration and repeated startup, then checks reads and writes after reopening.
The expected migration changes are records schema v14 to v16 and an empty
Strava transition ledger; the blob-reference index must also exist. Keep this historical fixture
fixed when adding later migrations.

`desktop-convergence-upgrade.test.ts` also loads a matrix generated by actual
branch-B runtime modules at `a0d50ef8fae5d7f75186c652d09244b19f736243`.
It covers incomplete ownership, fewer/disjoint/empty replacements, parity
verdicts, stale non-head proofs, and refusal after an unreceipted deletion.
The fixture includes actual legacy file bodies, populated import/reset ledgers,
and Claude archive claims and blobs. The cancelled-import and reset rows are
explicit synthetic SQL seeds; Oura and Claude state use B's runtime APIs.
The dump retains `sqlite_sequence`, including retired file IDs. Owner and
builder requests pass through
the real server before and after restart. The matrix is dumped before B's
reads refresh its saved verdicts and cursors. A fault at the PDPP version update
must roll back the index migration and preserve history before retry.

`desktop-dde-upgrade.test.ts` uses a second frozen fixture written by the
current `dde4ed94` runtime. Its two legacy file metadata rows are synthetic SQL
seeds; records, history, blobs and transition state use the historical APIs.
It checks its saved Strava export-to-browser
transition across migration, completion and reopen. The test preserves the
transition snapshots, archived records, history and blob state, and verifies
that stale-generation writes stay refused.
Startup preserves Strava archive claims through their transition ledger,
using the same rule as Claude archives. Owner erasure removes the ledger,
archived records and claims before collecting the unreferenced blobs.
A takeover reset drops only that scope's archive and unreferenced claims.
Unreadable retained history keeps ambiguous blobs until that history is removed.
