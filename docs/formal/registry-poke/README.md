# Registry change push: TLC model

`RegistryPoke.tla` models the gateway's "the registry moved" signal as a held request with a fallback probe, and checks the one property that matters: a device is never behind the registry by more than a bound.

The gateway keeps one counter, `seq`, that rises on every committed registry write. A device keeps `applied`: the `seq` its last pull read. Only a pull moves `applied`. A held request's reply and a probe are hints that start a pull. A reply may be lost; a request may break; the gateway may fail to wake a waiter.

The probe compares a marker that fingerprints one registry row. Another row stamped in the same millisecond leaves it equal, so a probe, or any pull that the marker gates, can find "nothing new" after a change (`ProbeBlind`). The model keeps that fault: the probe is not exact. What the device can rely on is the gateway's sequence: an answer whose sequence is above the device's cursor, and the first answer after a failure, start a cycle that does not look at the marker and does not wait for the probe (`ForcedPull`). Only a successful answer starts that cycle (`PullAfterFailure`); a failed or lost request and the re-subscription that follows call nothing, as in `change-push.ts`. After a failed request the device waits `BO` ticks before the next one (`BO` = 3, the 30 s cap of the shipped back-off, in every configuration except the ones marked `BO` = 0). The manager's own timer cycle (`TimerOn`, every `PT` = 6 ticks, 60 s) reads the registry exactly. With `Gate` it is skipped while the push covers it (see "The position gate").

`StaleBound` says `age[d] <= Bound` for every device, where `age` counts ticks since the oldest commit the device has not yet applied. One tick is about 10 s in the shipped settings: the held request waits `W` = 2 ticks (25 s) and is declared dead after `Slack` = 1 more (10 s); the probe period is `PL` = 1 (5 s), or in the older configurations `PH` = 6 (60 s) while the push is healthy, re-read at every probe tick so that a push that just failed returns to the short period at once; the timer cycle is `PT` = 6.

Run one configuration (one TLC job, 4 workers, `nice 19`):

    TLA2TOOLS=/path/to/tla2tools.jar docs/formal/registry-poke/run.sh P1-full-bound3

TLC 1.7.4, one device, two writes, 12 ticks. Raw output is in `out/`. P0 to P3 model an exact probe (`ProbeBlind=FALSE`) and no timer (`TimerOn=FALSE`); P4 onward use the shipped combination: a blind probe is possible and the timer runs.

## The position gate

The shipped manager no longer stretches the probe while the push is healthy. Each push answer reports the gateway's sequence as a position, and so does the answer that ends a wait with nothing new: the gateway reads the sequence again when the wait ends. A cycle started under position P reads the registry after P, so while the push is healthy and its position is still the one the last cycle started under, the timer's cycle and the probe would only repeat that read, and the manager skips both (`Gate`), for as long as that holds. There is no periodic check on the push: a change whose wake was lost is found by the next answer, whose position differs (`PositionCompare`), and a push that goes quiet is found by the unhealthy-turn cycle. A push that goes from healthy to not healthy starts a cycle at once (`PullOnUnhealthy`): while it was silent its position could not vouch for the registry. Without that cycle the gate is not safe: V9 is violated at 6 ticks, because a reply lost on the wire is noticed only at the request deadline (3 ticks), and the timer tick that follows may have been skipped just before. With it, the bound is the one the timer gave before: 6 holds (G1) and 5 does not (G1b); with every reply lost the push is never healthy, the gate never applies, and the result is P6's (G2).

What the position compare buys is shown with a cycle that fails (`CycleFails`, once per run; the manager's own retry after a failed cycle is left out of the model, so only the timer and the probe repair it). A failed cycle settles nothing, so the position it started under is no longer vouched for. With the compare the timer retries, the bound is 12 ticks (one timer period for the failure plus the timer's own 6), and 11 is not enough (G3, G3b). Without the compare, a healthy push covers the timer and the probe for ever and the device is left behind (V10, run to 20 ticks). The ungated model has the same 12 and 11 (P9, P9b): the gate costs nothing against the timer. Every older configuration runs with `Gate = FALSE`, `PullOnUnhealthy = FALSE`, `PositionCompare = TRUE` and `CycleFails = FALSE` and returns the verdict in the table above; only the state counts changed, because of the new variable.

## Reading the table

- **What starts a pull.** Only an answer: one above the cursor, or the first one after a failure. A lost reply, a request that times out and the re-subscription that follows start nothing. An earlier version of this model started a cycle on every reconnect; the code does not, so the earlier "3 ticks with every reply lost" did not describe it.
- **P6 / P6b: every reply lost with a blind probe is bounded by the timer, 6 ticks (60 s).** Nothing the push does can help while no answer arrives, and the probe may keep reading an equal marker. P6b shows 5 is not enough. The timer's 6 ticks hold whatever the back-off, because the back-off only spaces requests that cannot answer. P5 (any reply may be lost) gives the same 6.
- **P7 / P7b: with replies delivered, connections that break and a 30 s back-off bound it at 5 ticks (50 s), and 4 is not enough.** The earlier model had no back-off, so it could not show this term, and I did not isolate which faults make up the 5. With the first-retry back-off (`BO` = 0) the same faults hold at 2.
- **P8 / V7 / V7b: what the forced cycle buys.** With no faults beyond the marker's blindness, a pushed change is applied at once (bound 0). If the answer went through the marker gate like a probe tick, a blind marker would discard it, and the device would wait for the timer (V7 violated at 0, V7b passes only at 6). This is the defect `ForcedPull` removes. The cycle also skips the probe read, so a probe that never answers cannot hold it (see `sync-manager.push.test.ts`).
- **The marker a forced cycle leaves behind is not modelled, and the code is more conservative than the model.** The model's forced pull has no marker to publish. The manager's forced cycle reads no marker and publishes none: `pulledMarker` moves only to a marker read before its own cycle started, so a probe that answers during a forced cycle cannot mark a later registry state applied that the cycle never read. The next timed probe sees a marker that differs and runs one extra cycle. An extra cycle can only shorten how far a device is behind, so every bound in the table holds without a rerun (see `sync-manager.push.test.ts`).
- **Entry points the model leaves out: it under-counts cycles, so its bounds are pessimistic.** The manager starts a cycle from more places than the model has actions. `Timer` is the 60 s interval. `Probe` and `PokePull` are the timed probe and a pushed answer. Startup, an explicit `trigger()` and the debounced cycle after local ingest (`notifyNewData`) are unconditional cycles that read the registry exactly, like `Timer`, at moments the model does not list. Focus and online (`requestPull`) are probe pulls with the marker gate, like `Probe`, started early. A requested follow-up after a running cycle is one more such cycle; after a failed cycle it waits out the push's back-off (1 s doubling to 30 s) first, so it only adds cycles later than the model's own. Each extra cycle can only apply the registry sooner, and none can leave the device further behind, so leaving them out does not make a bound in the table worse. That is the only claim here; the table's bounds are not a guarantee for the code, because they hold under the model's assumptions, and the code departs from them in these ways:

  - **Every commit raises `seq`.** What a stream-sync cycle reads from the registry, and what raises `seq` for it (gateway migration 0069):
    - `GET /v1/data` and `GET /v1/data/:id` read `data_points`: control, stream and head rows, tombstones, generation and lineage fields on those rows. Insert, delete and any update of a client-visible column raise `seq` (settlement bookkeeping, nonces, payments and the signed payload are internal and raise nothing); the log protocol's writes are such rows.
    - The sync gate's `GET /v1/servers/:address` reads `servers`: registering, revoking, re-registering and removing a server raise `seq` (same internal-column rule). The gate asks only whether the row exists, so a revoked server still counts as registered to it.
    - Reads that nothing raises `seq` for: `GET /v1/data/:id/versions` (a tombstone's settlement status, read by the legacy cycle's deletion finality) and the blob store (content addressed, so a change needs a new registry row). The legacy cycle is therefore never settled: its retries (deletions waiting on finality, downloads in backoff, upload limits, lost-point checks) run on the clock. The stream-sync cycle reads neither.
    - Local inputs (Account mode, the local database, a run's commit) start cycles through `trigger`, `notifyNewData` and `notifyRecordsCommitted`, not through `seq`.

    A device whose push is healthy and whose position stands finds a write that no trigger covers only at its next cycle, which a later change, a failure of the push or a restart starts; no bound is claimed for it.

  - **Reads are instantaneous, and what a cycle leaves undone is retried only by the timer.** The model lets one cycle fail (`CycleFails`, G3 and after), which is why its bound is 12 and not 6. In the code a cycle counts as failed, and settles nothing, when it throws, is blocked, or reports a connection that failed or a stream whose publish backs off or is deferred; those cases are subsets of the model's failed cycle. The manager retries after the push's back-off (1 s doubling to 30 s) only when a request arrived during the failed cycle (a follow-up is owed); otherwise the ordinary timer is the retry, as in the model. A cycle that never ends, or work queued behind a running one, adds its own time to the bound.
  - **A cycle's duration, stop and pause are not modelled.** The visibility pause holds no timer and no request; the bound resumes at the first cycle after the tab is shown.
  - **Answers are trusted as they arrive.** The model keeps the larger of the last sequence seen and the reply. The code takes the reply as the new position. One request is in flight at a time and a late result is discarded, so a client cannot reorder its own answers; a gateway instance that answers with a lower sequence moves the position down, which differs from the one the last cycle started under and so costs one extra cycle, the safe direction.
  - **The gateway's restored database may lower `seq`.** A position that differs in either direction is a change to the client, so a cycle runs.

The model's cycle fails at most once and succeeds otherwise; the follow-up a rejecting cycle still owes is a scheduler property, tested in `sync-manager.push.test.ts` rather than modelled.

- **P4 / P4b / V8: the timer is the guarantee.** With no probe, push and timer hold at 6 ticks, and 5 is not enough. Remove the timer as well (V8) and a lost reply is never found: the push alone has no bound.
- **P1 / P1b / P2 / P3.** With an exact probe the probe alone is the repair: it returns to the short period as soon as a push fails, so a stale device is found within the request deadline (3 ticks), or within 1 tick when every reply is lost and the push never became healthy (P2). These rows say nothing about a blind probe; the shipped marker can be blind, which is why P4 onward carry the timer.
- **V4** violates: if the probe stretched to 60 s even when the push is not healthy, lost replies would leave a device behind for a whole stretched period. This is why the manager stretches only while healthy.
- **V1, V2, V6** violate. Each removes the probe and then one more repair.
- **P0**: with no faults and an exact probe a device is never behind at all.

A device pulls on an answer above its cursor (`lastSeen`), as the code does, not above what it applied. The device cannot see what it applied, so a pull that was discarded is not retried by a later answer that repeats the same sequence.
