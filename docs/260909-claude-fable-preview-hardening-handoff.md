## Scope discipline — explicit user instruction

This system is not in production. Optimize for a working product and convincing preview E2E, not production operations completeness. This instruction supersedes preservation, rollback and exhaustive-testing requirements in earlier plans and this handoff's historical evidence.

- **Preview TEEs are disposable.** Recreate or replace them and reset their test state when that is the simplest path. No obligation to preserve CVM/app identities, volumes, old OAuth connections or historical test owners. Fresh signup and reauthorization are acceptable after a deliberate rebuild. Update the actual SDK anchors/configuration if identities change; never bypass verification. Check resource boundaries so a preview reset does not erase unrelated shared Account/Web data.
- **No rollback or migration project.** Do not build backup/restore, reverse migration, legacy-mode restoration, snapshot rollback protection or controller disaster recovery. Existing historical rollback gaps are not work items. A clean redeploy and a fresh test owner are sufficient for this phase.
- **E2E proof has higher value than more unit tests.** Reproduce a concrete failure through the real UI/SDK/MCP path where practical, make a small fix, and rerun that flow. Add a focused automated regression only when it cheaply prevents recurrence or isolates logic that is difficult to exercise live. Do not create large mock matrices, duplicate existing coverage, chase coverage percentages or add dozens of speculative tests. Run existing relevant checks and required CI; do not remove useful tests.
- **One concrete outcome at a time.** Pick one user-visible failure or missing E2E proof. State the success condition, implement the smallest sufficient change, prove it, then move on. Do not turn a bug into a framework, platform, generalized abstraction or cross-repository cleanup.
- **The candidate list is a menu, not a mandatory release checklist.** Prioritize happy paths and observed failures. Expand failure injection, concurrency and soak coverage only as the working baseline and available time justify it. No exhaustive security, performance or operational matrix is required.
- **Stop when the chosen flow works and required checks pass.** Record a short proof and any actual remaining limitation. Do not invent adjacent hardening work to make the slice feel complete.

“E2E must not break” means preserve the supported product journeys after changes. It does not mean zero downtime for preview infrastructure or preserving a particular test session. Rebuilding preview resources is fine; finish by proving the normal flows again. Routine restart behavior can be tested as a product feature without turning it into an infrastructure-preservation requirement.

## Recommended hardening order and acceptance

1. **Get the final build working on preview.** Reuse or rebuild the preview, whichever is simpler. Use the final integrated source/package combination and valid preview-specific signed configuration. Prove normal SDK and Claude flows. No state migration, rollback path or preservation of old TEEs is required. Classify cold/warm state only when testing that behavior.
2. **Complete fresh-owner and data-update coverage on that build.** Normal signup, ingestion before enablement, explicit enclave setup, consent without Lite, read/decrypt/ACK; update data and grant another supported scope while warm. Simultaneous MCP/SDK/prewarm must create one owner startup and hydrate current versions before use. Investigate terminal DCR retry and cold-prewarm timeout through public UI/API regressions. No silent fallback to Lite on enclave failure.
3. **Kill a worker during a running SDK job.** Prove bounded retries, correct new generation/attempt, no stale completion/result acceptance, immutable result objects, correct consumer decryption and idempotent ACK. Stop once that bounded scenario works. Lost responses, duplicate requests, upload interruptions and network partitions are optional follow-ups if a concrete failure warrants them, not an obligatory matrix.
4. **Revocation, isolation and re-enable.** Two independent test owners; cross-owner grant/data/job/result-handle denial, wrong chain and ungranted scope. Exercise fresh and cached delegation checks through the documented 60-second window, ordinary/result writes, queued/running work, result-handle retrieval and re-enable. Confirm old grants/identities do not silently regain authority. Public result GET/HEAD returns ciphertext by design; never treat ciphertext availability or already-delivered plaintext as a revocation defect or promise cryptographic erasure.
5. **MCP user flows.** Prove browser-closed cold wake, refresh/reconnect and the tools apps actually use. A routine controller restart check is useful if inexpensive. Controller replacement/state recovery, legacy rollback and disaster-recovery machinery are out of scope; rebuilding and reauthorizing is acceptable.
6. **A small mixed-workload soak, if time remains.** Run ordinary owner updates, MCP and SDK jobs; inspect existing logs for leaks, stuck jobs and cleanup failures. Fix observed problems. Do not build a monitoring platform, comprehensive benchmark suite or deployment framework. Prebuilt images are optional if they solve an observed startup problem with a small change.

Avoid spending this window on DRK redesign, automatic KMS migration, a new key-management platform, multi-controller HA, broad refactoring or mainnet enablement. Do not redesign the v1 key/ciphertext contract or weaken current attestations/fences to simplify testing. This code-compatibility constraint does not require retaining preview test identities or data. Do not delete `packages/lite` or break retained Lite/full-PS/direct clients; inventory and test those dependencies before retirement.

## Non-regression working contract

Prefer a failing real E2E reproduction, a minimal fix, and a passing rerun. Use small targeted tests where useful and run existing relevant checks/required CI. Do not require a new unit test for every edit or a full test/review campaign for a small change. The user's E2E-first instruction takes precedence over older blanket testing rules for this work.

For each change, rerun the affected user journey plus a quick SDK/Claude sanity check if shared runtime behavior changed. Run the broader golden flows once on an integrated preview candidate: owner ingestion/update, stored-data consent without Lite, SDK result/decrypt/real ACK, Claude authorization/read and browser-closed wake. Worker-stop recovery is a separate focused experiment, not something to repeat after every edit. Keep unproven cases labeled pending.

Serialize shared fleet mutations so test results remain understandable. Temporary preview downtime and deliberate rebuilds are acceptable. Finish each experiment with a usable preview or explicitly record what remains broken. Keep secrets out of logs/reports. A concise record of tested refs, environment, normal client actions, job/result/ACK outcome and actual limitations is enough; do not build an evidence-management system.
