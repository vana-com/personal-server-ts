## 1. Cross-surface order (moksha first; mainnet gated on it)

1. Merge **vana-sdk #211 → main**. `release.yml` runs `semantic-release` on push to main → publishes `@opendatalabs/vana-sdk` (version decided by conventional commits). Record it.
2. Re-pin that version in **personal-server-ts #245** (5 manifests + lockfile), **data-gateway #100** (devDep), **lorebook #1**. Re-run each CI.
3. Apply data-gateway migrations to the **moksha** Neon branch: the 0048–0051 backlog (B3) if unapplied, then `0053`, `0054`, `0055`, `0056` in order, out of band, statement-by-statement.
4. Add the 7 gateway env vars to Vercel project **dp-rpc-moksha** (production) with `PREWARM_ENABLED` **unset/false**.
5. Merge **data-gateway #100 → main**; confirm `dp-rpc.moksha.vana.org` deploy and that `/v1/cron/jobs-sweep` is registered.
6. Merge **vana-storage #24 → dev** (auto-deploys dev), settle B2, then **dev → main** (`deploy-prod.yml`, `wrangler deploy --env production`).
7. Add the **R2 lifecycle rule** on prefix `jobresults/` to bucket `vana-storage` (and `vana-storage-dev`). Manual; no wrangler support.
8. Merge **personal-server-ts #245 → main**. `docker.yml` on `main` pushes `vanaorg/personal-server:<sha>` and emits the `images.env` artifact. Download it.
9. Provision the moksha CVM(s) on Phala with `GIT_REF` = that main SHA, `PS_IMAGE`/`PS_IMAGE_REF` from `images.env`, digest-pinned `AGENT_IMAGE`/`DIND_IMAGE`. Then `replicate.sh` for each extra node (same `app_id`).
10. Capture `app_id` and the uncompressed KMS root (`node scripts/tee/kms-root.mjs`). Set `ENCLAVE_KMS_ROOT_PUBKEY` + `ENCLAVE_APP_ID_ALLOWLIST` on **dp-rpc-moksha**; redeploy.
11. Register each node (`POST /v1/tee-nodes`, operator bearer), wait for a heartbeat carrying the expected compose hash, then `POST /v1/tee-nodes/<id>/admit`.
12. **SDK release #2** filling `ENCLAVE_TRUST_ANCHORS[14800]` from step 10 (B1). Re-pin it everywhere from step 2.
13. Apply account migrations `026` then `027` to the production account DB; add the Web/Account env vars; merge **unity-surfaces #987 → dev**, then **dev → main** (`vana-web-prod`, `vana-account-prod`).
14. Update the **Privy policy** to the 5-rule shape (§6) before Mobile sign-in traffic; validate-only, manual in the dashboard.
15. Merge **lorebook #1 → main**, set its env, provision Redis. Then run the verification gate (§7) and only afterwards repeat 3–13 for **mainnet** (§8).

## 4. Migrations

**data-gateway** — hand-written SQL, applied **out of band**; `npm run db:migrate` (drizzle-kit) is explicitly _not_ the mechanism and the journal is stale. Credential: `NEON_URL` for the target Neon branch. Order: backlog (B3) → `0053_identity.sql` → `0054_jobs.sql` → `0055_grants_expires_at_timestamptz.sql` → `0056_identity_last_prewarm_at.sql`. All four are idempotent (verified: 4/4, 12/12, 1/1, 1/1 guarded statements). `0055` briefly takes an `ACCESS EXCLUSIVE` lock — quiet window, no long transactions. Apply **before** deploying, and `0056` before setting `PREWARM_ENABLED`.

**unity-surfaces (account DB)** — `ACCOUNT_DB_MIGRATE_ALLOW_REMOTE=true DATABASE_URL=… node apps/account/scripts/migrate-account-db.mjs --allow-remote`. Both flags are mandatory for a non-localhost host; the runner tracks applied filenames in `_migrations` and wraps each file in a transaction. `026` and `027` both `DROP CONSTRAINT IF EXISTS` then re-add `mobile_sessions_scope_check`; `027` supersedes `026`'s value, so both are re-runnable and order-tolerant. ## 6. Privy policy — exactly what the code validates

`apps/account/src/lib/mobile-attestation/mobile-signer-bootstrap.ts` is validate-only and fails Mobile sign-in closed with `mobile_signer_bootstrap_unavailable` on any mismatch. Policy object: `chain_type = "ethereum"`, `version = "1.0"`, `id = ACCOUNT_MOBILE_PRIVY_POLICY_IDS` (exactly one id), `owner_id = ACCOUNT_MOBILE_PRIVY_POLICY_OWNER_ID`, and **exactly 5 rules** (`SUPPORTED_VANA_CHAIN_IDS × 2 + 1`) — an extra rule fails validation.

1. One `personal_sign` rule, `action: ALLOW`, exactly one condition: `{field: "content", field_source: "message", operator: "eq", value: "vana-master-key-v1"}`.
   2–5. Four `eth_signTypedData_v4` rules, `action: ALLOW`, **three conditions each** — one `ServerRegistration` and one `PrewarmRequest` rule for each of `"1480"` and `"14800"` (chain ids are **strings**).

- `ServerRegistration` rule: `{chainId, ethereum_typed_data_domain, eq, "<chainId>"}`, `{verifyingContract, ethereum_typed_data_domain, eq, <ACCOUNT_DATA_PORTABILITY_SERVERS_CONTRACT>}`, `{serverUrl, ethereum_typed_data_message, starts_with, "https://", typed_data: {primary_type: "ServerRegistration", types: {ServerRegistration: [ownerAddress address, serverAddress address, publicKey string, serverUrl string]}}}`.
- `PrewarmRequest` rule: `{chainId, ethereum_typed_data_domain, eq, "<chainId>"}`, `{verifyingContract, ethereum_typed_data_domain, eq, <same contract>}`, `{chainId, ethereum_typed_data_message, eq, "<chainId>", typed_data: {primary_type: "PrewarmRequest", types: {PrewarmRequest: [ownerAddress address, chainId uint256, scope string, expiresAt uint256]}}}`.

The signer is also validated: `authorization_threshold = 1`, exactly one authorization key with a non-empty `public_key`, and `user_ids` absent or empty.

## 8. What differs for mainnet

`CHAIN_ID=1480`; the mainnet contract set (B5); a **separate** `app_id` and KMS root from an independently provisioned CVM fleet — a fresh `provision.sh` deliberately produces a new `app_id`, so mainnet and moksha nodes cannot decrypt each other's jobs; `STORAGE_API_URL=https://storage.vana.org` and the `vana-storage` prod bucket; gateway project `dp-rpc` (`dp-rpc.vana.org`); `ENCLAVE_TRUST_ANCHORS[1480]` filled by a third SDK release (or the same one as step 12 if both fleets exist first); `NEXT_PUBLIC_PS_MAINNET_DISABLED` flipped off on `vana-web-prod`.
