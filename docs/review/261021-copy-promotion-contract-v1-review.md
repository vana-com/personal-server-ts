Verdict: request contract changes before implementation. Fingerprint-pinned selection is the right direction, but the supplied function is not a total model of the promised state machine, and it is not a drop-in replacement at this head.

Scope and evidence: read only all 15 allowlisted files in vana-com/personal-server-ts at exactly 355fbf3192cdadc4e41f3c6e9af860217c56df7e through commit-pinned GitHub reads. No edits, tests, publication, Work/Codex tasks or model APIs. Cancellation/authority and owner_notes rechecked immediately before report: not cancelled/revoked; no owner notes. Citations below are repository path:line at that SHA. The proposed contract is the assignment brief, not code present at this SHA.

1. BLOCKING: rule 6 cannot be represented or enforced by the proposed function.
Input contains only one optional finalized fingerprint; output has no terminal-integrity-conflict variant. Sequence: retain A and B, verify finalized A, promote A, later verify incompatible finalized B. Calling the function with B is indistinguishable from a first valid observation of B and selects B; calling with A ignores the contradiction. This holds even before promotion if two verified observations already exist. Add explicit conflict outcome and persisted, identity/domain-bound finalized evidence history (or a trusted precomputed conflicting-evidence state), plus a persisted promoted fingerprint and absorbing terminal status. A successful retry must never clear terminal conflict. Existing evidence carries chainId, registry, owner, scope, block number/hash, version/status (core replication/dpv2.ts:35-52); stripping it to one fingerprint loses the facts needed to diagnose and distinguish histories. Lite currently refuses a differing finalized fingerprint after confirmation (lite/canonical-store.ts:1123-1129), so replacing this guard with latest-fingerprint selection would regress safety.

2. BLOCKING: fingerprint equality is not a substitute for verified-copy validity, and promotion step 3 destroys corruption classification.
Sequence: C is retained as corruption because its bytes fail its claimed hash or its envelope is invalid; valid A matches finality. Promotion step 3 changes every other reason to copy_conflict, exposing C's values to the owner contrary to the contract. A corrupt copy whose claimed pair-vector fingerprint matches finality is also indistinguishable from a verified eligible copy in BatchCopy. Preserve corruption and finalized_conflict reasons, exclude invalid copies from promotion, and specify monotonic reason precedence or separate validity from selection status. A matching hash-vector does not prove the retained bytes actually hash to it. Existing codec independently validates bindings/chunk hashes and complete assembly (core replication/transport.ts:96-120,209-250), and Lite validates the envelope before retention (lite/canonical-store.ts:1040-1049). Those gates must survive the common selector. If malformed envelopes are retained for diagnostics, envelope_json alone cannot be treated as a validated envelope on the read path.

3. BLOCKING: the contract's fingerprint is not the current Lite fingerprint or a directly recoverable on-chain digest.
Lite computes sha256:<hex> over canonical envelope JSON (lite/canonical-store.ts:62-66,469-472,1050). The contract defines unprefixed hex SHA-256 over ordered fragment hash pairs. DPv2 stores keccak256(ABI(dataHash, metadataHash)), not hash-pair preimages or the proposed batch SHA (core replication/dpv2.ts:34-60). Evidence obtains preimages from Gateway head and separately checks their chain commitment (evidence.ts:187-219; dpv2.ts:178-183). If finalized chain says F but Gateway supplies only mismatching head G, the adapter can establish a mismatch but cannot manufacture F's pair-vector fingerprint. The new type needs an explicit finalized-slot mismatch/unknown-preimage state or a verified vector construction stage with a specified retry outcome. Otherwise undefined may incorrectly cause Wait(finality) when finality is already known but the matching preimages need re-observation. Define canonical hash casing/prefix, index order, fragment count/completeness and domain/identity binding, and retain both transport fingerprint and envelope digest where needed. Simply passing the new fingerprint to existing promotePending quarantines the sole valid envelope as divergent.

4. Reorg/unavailability and status transitions need an explicit adapter contract, not an inferred fingerprint.
Current evidence checks the pinned finalized block again after all I/O and throws retryable ReplicaEvidenceUnavailableError if it changed (core replication/evidence.ts:221-248). A Gateway optimistic head rollback only yields pending, while finalized currentVersion>1 or expected-pair mismatch yields conflict (dpv2.ts:133-177). Preserve those distinctions. Sequence: A staged; optimistic A head rolls back or block hash changes during verification; then valid B is observed. The first failure must not become terminal finalized contradiction or authority for A. Conversely A verified at an earlier finalized block followed by incompatible finalized B requires retained history and terminal behavior, not ordinary recoverable replacement. Define behavior for already-promoted A when a later read is unavailable/inactive or a finality assumption is revoked: wait is only a work result, not a specified canonical read/ack rollback policy. Do not silently demote confirmed data on an ordinary transient read. Also keep predecessor verification as an explicit precondition; the existing decision doc requires every member and predecessor, and transport encodes sequence/previous (transport.ts:19-24,104-111). A matching vector alone is not that proof.

5. Arrival after promotion and repeated refetch need durable transitions.
Sequence: promote A and acknowledge work; B arrives later. The function can return promote A with B quarantined only if it is actually re-entered with retained A and finality. Contract does not state that acknowledged work is reopened/reconciled for late copies, or whether duplicate promotion/ack is idempotent. Require late-copy staging to retain B and apply its quarantine atomically without losing A's confirmed state or duplicating ack. Current Lite rejects B before retaining it because the key is id-only (lite/canonical-store.ts:62,1054-1059). Same-copy retries after quarantine simply return quarantined and cannot recover (1058-1059,1139-1140).
Refetch sequence: finality A, retained B, fetch C, fetch D, none match. Required result remains refetch, with B/C/D retained, until one batch-level budget is exhausted; new fingerprints must not reset attempts indefinitely. Specify how mismatch-only fetches count as failures, how Wait(owner) survives restart, and which later valid evidence/copy can resume work. Those states are not inputs/outputs of the pure function; assign them explicitly to durable coordinator transitions rather than claiming the function alone is total.

6. Visibility goal is a policy change, not behavior consistent with the existing signature.
core replication/visibility-policy.ts:15-25 hides every quarantined copy from both readers; conflicted is owner-visible only for origin=local. It accepts no reason. Current account-conflict marker is "account conflict", not copy conflict (37-47). Grant include-pending is configurable (6-14,24), so merely leaving unmatched copies pending would leak them under that mode. Add reason-aware copy policy with unconditional grant denial for copy_conflict/finalized_conflict, unconditional both-reader denial for corruption, and do not broaden unrelated received account conflicts.
Sequence: two valid conflicting copies before finality; function returns only wait, without quarantine list. If stage leaves them pending, configured grant include-pending can expose their effects. Define staging/classification of all copies on wait, including the zero/one-copy cases. Promotion must clear the selected copy's old reason: state=confirmed with old copy_conflict violates the contract's non-null reason invariant. The shown SQL does not enforce reason=>quarantined; enforce it in SQL or explicitly in all transitions.
For showing BOTH values, fingerprint-keyed pending storage alone is insufficient: Lite point reads return one row, and preview uses the ordinary reducer/one-row key (lite/canonical-store.ts:68-80,1018-1026; core replication/record-reducer.ts:37-53). Conflicting same-operation variants can suppress a whole connection (merge-plan.ts:83-99,123-126). Keep conflict diagnostics/variants separate from canonical winner materialization or define a read result capable of returning both marked values, while grants continue reading the confirmed predecessor. No-values finalized-conflict diagnostics also need a separate safe representation.

7. Existing call sites and clean-replacement assessment.
- Lite stagePending is first-retention-wins in storage only: the first envelope remains, later different content throws (1054-1059). It does NOT automatically promote the first arrival and has no size/counter-based batch-copy selector. Reversed arrivals change which evidence is retained, which the new retention model must fix.
- Lite promotePending chooses the one retained envelope by exact envelope fingerprint, refuses quarantined values, and quarantines mismatch (1109-1149); commit rechecks pending state/fingerprint within the actual import transaction (474-484) and atomically writes receipt/confirmed state/index withdrawal (706-717). Preserve that transaction guard; preliminary decision must not be the only authorization against concurrent staging/finality changes.
- Public Lite import directly calls commit without a promotion input (1209-1215); commit authenticates but only applies the pending gate when promotion exists (454-484). If "every Lite import consumes CopyDecision" is literal, this bypass must be gated or explicitly designated a separate trusted already-finalized path with proof requirements.
- Import receipts remain id-keyed and reject different envelope content under the same id (488-495). Pending refs and blob-active refs are batch-id keyed, not copy-keyed (909; 979-983). Updating retention only does not make copy-specific withdrawal/repair clean.
- core transport.ts is fragment codec/assembly, not a batch selector. It sorts by fragment index and rejects inconsistent copies; size controls fragmentation limits, not authority (145-205,213-250).
- Lamport counter ordering in merge-plan.ts:195-229, revision.ts:9-21 and completion.ts's selectStreamCompletion selects record/receipt operations, not alternative transport copies. Do NOT replace these with CopyDecision: distinct-writer concurrency remains a separate ordering contract.

Totality checklist for a revised contract: validate one identity and normalized unique fingerprints; zero copies + no authority => wait, zero copies + known retrievable finalized target => refetch; one/many eligible copies + one verified authority => promote exact match or refetch; unavailable/unfinalized evidence => wait without promotion; incompatible durable finalized facts => terminal conflict; corrupt matching copy => not promotable; already-promoted matching copy => idempotent reconcile/ack; late copies => retain/classify; mismatching refetch => persistent bounded retry/owner wait. Sort/deduplicate quarantine output so replay multiplicity and arrival permutation do not change the returned decision (compare existing deterministic normalization in merge-plan.ts:234-260).
